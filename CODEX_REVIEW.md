# GeoSense independent review

**Date:** 2026-10-01  
**Scope:** Baseline review of code, documentation, and `data/POLICE_STATION.xlsx` before the subsequent safety edits. The workbook data was not changed and no Google or AI API calls were made.

## Decision

**Clarified objective from the owner:** Given an address, show three real, nearby police stations with distances so an officer can select a suitable one. An applicant's chosen station may be a guess. There is no requirement that GeoSense reproduce that one station name when several stations are similarly close. The baseline is suitable for a supervised proximity aid only after output distances and missing/stacked coordinate limitations are made visible; its top-three proximity quality is not yet measured across states. The 395 stacked-coordinate rows and coarse or incorrect address geocodes can make the displayed order falsely precise.

**Implementation after this baseline review:** v2 now ranks located rows across the address's state by distance and displays up to three candidates. Supplied PS and district names do not restrict address lookups. When the state is omitted, the state in Google's address result must match one workbook state. Routine lookups do not geocode blank station rows; shared coordinates are flagged. The source workbook was not edited. These code changes have only been inspected statically because this machine has no Python executable on PATH; the offline tests and a live address sample remain to be run before operational use.

The design's useful properties remain: returned station names are drawn from the sheet; state lists and prompts are derived from `STATE`; and most station coordinates are present. The key design question is whether an address query consistently returns the **nearest three** across the relevant search area, even when the applicant supplied a guessed PS or district. The current ladder can stop early on a typed PS or locality and show fewer than three stations (`v2/engine.py:90-135,316-372`), or restrict to a supplied district (`:140-307`). That behavior needs to be reconciled with the clarified objective.

## Findings, ranked by severity

### High — The current log cannot measure the clarified objective

The `LookupLogs` sheet has 27 data rows. `C2:C27` (`ACTUAL PS KNOWN`) and `D2:D27` (`PREDICTED PS`) are populated; none of the 26 names matches exactly. **This is not a failure rate for GeoSense's clarified task.** The officer confirmed those actual stations are valid and close, and other nearby stations can also be suitable. The log stores only the selected result, not all three candidates or their distances (`common/lookup_log.py:54-76,101-121`), so top-three recall and distance quality cannot be reconstructed. Row 28 has no actual value. `F2:F27` (`MATCH`) contain formulas without cached results and implement exact-name comparison, which is the wrong success metric for this use case.

**Correction to an earlier analysis:** 22 of the 26 labelled rows have a blank `PREDICTED DISTRICT`, so a cross-district conclusion from that column is invalid. A local coordinate comparison can be made for 25 pairs of actual and predicted station names: choosing the minimum distance where a name repeats, **15 pairs are within 3 km, 20 within 10 km, and 23 within 20 km**. The median is about 1.8 km; one actual name has no verbatim master match. These are distances *between station coordinates*, not from the applicant address. Repeated names and bad coordinates can bias them downward. They suggest exact-name mismatch overstates the problem but do not establish that the predicted station was in the closest three.

**Effect:** The workbook has officer-provided reference stations, contrary to the brief, but its exact-match `MATCH` formula is unsuitable for the owner's clarified objective. The former visible labels “Very Likely” and “Guaranteed” were uncalibrated (`common/output.py:21-27` in the baseline). Measure whether the officer-confirmed station is in the displayed top three, whether another displayed station is comparably close, the distance gap to the true nearest eligible station, and the rate of bad or missing coordinates. Record all three candidates, their displayed distances, selected station, and address geocode quality for future evaluations.

### High — 395 rows participate in different-name coordinate stacks

I independently read the workbook's XML and reproduced the brief's stated definition: **395 rows at 130 exact coordinate points** have at least two distinct station names after removing nonletters. That is 13.2% of all 3,000 rows, but it is **not** the measured error rate. Cluster sizes: 78 pairs (156 rows), 25 triples (75), nine fours (36), seven fives (35), three sixes (18), three sevens (21), two eights (16), one nine (9), one eleven (11), and one eighteen (18). The 52 clusters of size at least three contain 239 rows. The 18-way Madurai Rural cluster includes different town and taluk names; the 11-way Ramagundam cluster crosses two police districts. This strongly suggests fallback to a common POI or area point, but coordinate equality alone cannot prove which individual rows are wrong. The brief's per-state figures (116 AP + 193 TN + 122 TS = 431) do not reconcile with its total. Recomputed row counts are **AP 117, TN 160, TS 118 = 395**.

The existing guards cannot see a same-district stack. `geocode_station()` accepts the first Google result after broad India/state/type and sibling checks (`v2/geopy_distance.py:385-423`); the sibling check regards a stacked neighbor as zero distance (`:443-455`). The audit only rechecks isolated rows (`:458-474`), and the bulk script repeats that same rule (`scripts/build_ps_coords.py:156-169`). Equal distances then preserve sheet order in `rank_ps_by_distance()` (`v2/geopy_distance.py:714-734`), making ranking arbitrary within a stack.

**Estimate:** About **200–300 of the 395** are plausible wrong station locations, a triage estimate rather than a measured fact. One correct location per size-3+ cluster would leave 187 questionable rows already; some clusters may have multiple real colocations, and some of the 156 paired rows may be wrong. A stratified manual audit is required to estimate the genuine error rate. Treat every unverified stack as uncertain meanwhile.

**Proposed fix:** At fill time, compare each candidate coordinate against **all accepted rows and the pending batch**, including the first rows of a new state. A different-name collision should create a *review state*, not automatically erase either coordinate. Normalize only naming noise (station code, `PS`/`P.S`, punctuation, spacing) for comparison; preserve original rows and distinguish station categories such as AWPS and Town/Rural. Accept an exact collision as a legitimate colocation only with independent evidence: a verified station address/POI, an authoritative location, or explicit officer confirmation. Same-name historical district duplicates can share one verified location while remaining separate output rows. Store provenance, Google place ID/name/type, query, and review decision outside the station columns (for example an audit file or `LookupLogs`-independent review ledger); keep only `LAT`/`LNG` as writable station columns. Where unresolved, mark coordinate quality unknown and prevent distance-only `HIGH` confidence.

**Places evaluation:** Google's Places Text Search (New) can return `displayName`, `location`, `formattedAddress`, `types`, and place ID, which allow a name/type/address check unavailable from a bare coordinate. It still may return a nearby or similarly named POI; fuzzy name agreement alone is insufficient. Query the cleaned station name plus district/state, inspect several results, compare aliases and administrative context, and reject ambiguous matches to manual review. Use a location bias derived from *independently verified* district siblings, never from the stack being investigated. For a new state with no verified siblings, use the state text from the row and Google's administrative response; do not invent a region box. Do not use Google's returned result name as a substitute for the authoritative station row.

**Alternatives:** A local collision detector costs zero API calls and should run first. A second Geocoding query with name variants might help some rows but still lacks a reliable returned place-name check. Authoritative station coordinates or officer-confirmed pins are stronger evidence where available. Reverse geocoding a stack can identify what sits at the point but usually cannot locate each missing station.

**Cost / risk / verification:** A first Places pass over 395 rows is at most 395 Text Search calls, about **US$12.64 at Google's current US$32/1,000 list tier**, before monthly free usage, taxes, retries, or account-specific pricing. A 20-row trial is about US$0.64 at that tier. A second query for each unresolved row would double the calls. The main risk is confidently accepting a wrong same-name POI or rejecting legitimate colocations. Trial 20 rows sampled across states, cluster sizes, AWPS/old-district cases, and new-state-like sparse districts; have an officer verify the candidate coordinates independently. Then audit a stratified sample of at least 30 clusters to estimate error/colocation proportions before bulk remediation. Official [Text Search fields and bias documentation](https://developers.google.com/maps/documentation/places/web-service/text-search) and [Google's pricing table](https://developers.google.com/maps/billing-and-pricing/pricing) support the API and list-price assumptions.

### High — Address geocoding and district selection can yield confident wrong stations

`geocode_address()` originally took Google's **first** result without checking result type, state, precision, or input PIN (`v2/geopy_distance.py:62-98` at baseline). Station geocodes had more checks than user addresses. Case 3b chose only the first text-matched district (`v2/engine.py:377-381`); Case 3c concatenated results from two inferred districts without a global sort (`:450-479`); and Case 3n searched all states when no state was named (`:410-446`). These different paths did not consistently implement the owner's “three nearest” objective. State text detection is fuzzy and a single detected state becomes a hard filter (`common/state_filter.py:71-118`); a false positive excludes nearby candidates.

**Proposed fix:** Preserve Google's formatted address, result types, precision, and administrative components for the *input* address; compare state and PIN when supplied; reject or flag coarse/contradictory geocodes. Rank the same candidate set globally by distance instead of stopping when an applicant's guessed PS or a text locality matches. Return an explicit “address location uncertain” result when signals conflict. Local logic costs no additional calls if the existing geocode response suffices; a second targeted geocode on ambiguous input adds one Geocoding call (about **US$0.005** list tier). Risk is more abstentions; verify on labelled near-boundary, stale-district, ambiguous-place, and wrong-PIN cases. [Google's Geocoding pricing](https://developers.google.com/maps/billing-and-pricing/pricing) lists US$5/1,000 above its monthly free cap.

### High — Blank coordinates cause repeated paid retries and incomplete rankings

There are exactly **14 blank-coordinate rows**: two TS, one AP, and eleven TN. The reasons in the brief are consistent with the code's rejection paths, but were not revalidated against Google. A blank is retried during every applicable district lookup (`v2/geopy_distance.py:687-705`) and during every bulk fill (`scripts/build_ps_coords.py:110-153`). Thus “geocoded once ever” is true only for successful rows; permanent failures repeatedly cost calls and delay lookups. Case 2 removes unlocated stations from a nonempty ranking (`v2/engine.py:175-178,228-290`); they are merely noted, and the true station may be missing from the top three. If no station can be ranked, it returns the first three sheet rows at `LOW` (`:180-226`), which are not spatial candidates.

**Proposed fix:** Maintain an external geocode-attempt ledger with status, reason, last attempt, and cooldown; never rewrite station names. Try name variants in a controlled order, including preserving and separately searching parenthetical qualifiers such as `RAIPOL (BEGAMPET)`. Search Places using district/state and verified sibling-area bias where available; ambiguous hits go to officer review or hand-entered verified coordinates. Do not use the failed candidate's own stack as the bias. Show excluded stations and an incomplete-ranking warning prominently; cap automatic retries per lookup. A first Places pass is 14 calls (about **US$0.45** list tier); one extra Geocoding variant each is 14 calls (about **US$0.07**). Manual verification is the main labor cost. Verify that each accepted point has station-specific evidence and that repeated lookups of unresolved rows make zero new calls within the cooldown.

### Medium — Tamil Nadu/AP station naming bypasses the intended text rung

The matching pipeline normalizes hyphens and PS words, but `_normalize()` leaves numeric prefixes, dots, parentheses, and joined versus split words (`common/matcher.py:75-95`). `locality_score()` compares the full candidate name (`:342-380`), and locality scanning supplies raw sheet names (`:491-537`). Thus address `ANNA NAGAR` is not treated as the same canonical phrase as workbook `K-4 ANNANAGAR` (confirmed in the TN sheet), even though `clean_station_name()` strips that code **for geocoding only** (`v2/geopy_distance.py:312-338`). The same issue applies to `P.S`, AWPS, `U/G`, and parentheticals. This is a coverage gap, not proof that every such address fails: fuzzy scoring may occasionally clear the cutoff, and v2 can fall back to distance. v1 has no measured equivalent fallback accuracy.

The four matcher invariants are sensible guards, but they are not a correctness proof for new naming systems. I1's four-letter minimum can exclude genuine short names or initials (`common/matcher.py:306-339`); I2's length penalty can suppress legitimate joined/split forms (`:342-380`); I3's fixed mass-tie width can cause different behavior as states are added (`:413-425`); I4 makes ties deterministic, but alphabetical order is not evidence of which stations are actually nearest (`:383-410`). `state_stopwords()` is data-driven, but retains a state word whenever any station/district contains it (`:277-294`), which can reintroduce generic tokens such as `TAMIL` across the full data set.

**Proposed fix:** Build a code-side alias index per row from the same cleaning rules used for geocoding, plus space-insensitive forms and carefully validated abbreviations. Keep row identities and raw display names. Apply strict whole-alias matching and retain the existing ambiguity/mass-tie gates; do not turn every suffix or short token into an alias. Cost: zero API calls and local CPU only. Risk: alias collisions across real stations; verify on positive and negative TN/AP cases, including `ANNA NAGAR`/`K-4 ANNANAGAR`, AWPS versus regular PS, `II TOWN` versus `I TOWN`, and short-token junk addresses.

### Medium — Historical district duplicates need explicit presentation and scoring

The workbook has **63 `(STATE, station name)` groups spanning multiple districts, covering 134 rows**; this includes genuine same-name stations as well as historical duplicate listings, so 134 is not a duplicate-error count. The matcher keeps `(DISTRICT, PS)` pairs (`common/matcher.py:141-189,510-519`), which respects the no-row-changes rule, but a lookup can use two top-three slots for one physical station. The cache also uses `(DISTRICT, PS)` rather than a physical site identifier (`v2/geopy_distance.py:252-309`), so identical old/new-district records are geocoded and assessed independently.

**Proposed fix:** Keep every source row but add a *presentation-only* equivalence group when strong evidence shows the same physical station (verified place ID/location plus compatible name, or human confirmation). Display one candidate with all source district labels and preserve selectable row IDs for logging. Distinct same-name stations must remain separate. Rank physical candidates before expanding row choices; if the district label is disputed or stale, say so. Cost: local processing and review, no routine API call beyond coordinate verification. Risk: incorrectly grouping two stations; verify against all 63 cross-district name groups and the Vellore/Ranipet/Tirupathur cases with an officer.

### Medium — CLI workbook override splits the source of truth

`--excel` changes the DataFrame and log path (`common/cli.py:64-86`), but `v2/geopy_distance.py` loads/writes the module-level `EXCEL_FILE` (`:270,516-563`) rather than the supplied path. A user can therefore match against one workbook, rank with coordinates from another, and log to the first. This is a correctness and data-integrity defect. Pass the selected workbook path through the engine and coordinate layer, with cache keyed by path and workbook identity. Zero API calls in a local regression test; risk is moderate refactoring. Verify two disposable workbooks with deliberately different coordinates and confirm each lookup uses only its selected file.

### Medium — Measurement, test, and operational controls are insufficient

`tests/validate_test_cases.py` covers 22 checks, but its seven real-address cases are Telangana-only and explicitly accept one known wrong rank-1 result. Paid geocoding/AI are mocked, so the suite does not establish live accuracy or the September/October coordinate changes. It also does not test `clean_station_name`, local-script state fallback, vague-result rejection, sibling/batch audit, retry behavior, or TN/AP name formats. `ARCHITECTURE.md` still describes a nine-check suite and a narrower ladder, so operational documentation is stale. The lookup log stores the chosen result but not all top-three candidates, method, input geocode, coordinate provenance, or whether a human overrode the first suggestion (`common/lookup_log.py:79-121`). No-result cases are not logged (`:90-95`), biasing any accuracy summary.

**Proposed measurement:** Run a prospective shadow evaluation with **about 100 consecutive or randomly sampled lookups per state**, stratified by applicant-guessed PS/district, urban/rural, boundary cases, name variants, and stacked/unstacked stations. Have officers identify one or more acceptable nearby stations independently of the display. Record top-three acceptable-station coverage, the distance gap between the displayed choices and the nearest verified coordinates, missing/stacked-coordinate rate, address-geocode failures, and whether the officer accepted a displayed choice. Include no-result cases in the denominator. Set acceptance thresholds with the owner before seeing results. Compare v1 and v2 on the same addresses only if v1 is kept. A local fixture suite costs zero API calls; 300 warm v2 lookups would ordinarily make about 300 Geocoding calls (about **US$1.50** list tier), plus any AI calls. The largest cost is officer review. Risk is selection bias and disagreement over what counts as an acceptable nearby station; double-review disputed cases.

**Availability/cost:** Geocoding exceptions return `None` (`v2/geopy_distance.py:62-79`); the engine may fall through to AI or empty output (`v2/engine.py:448-494`). The AI parser is tolerant of invalid JSON only by returning no district (`v2/ai_engine.py:69-97`). Add explicit failure and call-count telemetry, request timeouts/retry limits, and a human-review outcome. Do not silently fill missing coordinates during an ordinary lookup without a configurable call cap. The project folder is not a git repository (`git status --short` returned “not a git repository”); the three Excel backups do not provide code history. Initialize version control after the owner approves a baseline, without changing the source rows.

## Recommended sequence for owner decision

1. **Measure the clarified target.** Capture the three displayed candidates and distances for each lookup, along with the officer's acceptable nearby choices. Retire exact-name `MATCH` as the primary success metric.
2. **Run local collision detection and a 20-call Places trial**, with independent officer verification; keep unresolved coordinates out of confident distance ranking. Fix the 14 blank-row retry loop and address-geocode checks at the same time.
3. **Add row-preserving aliases and duplicate presentation**, then test TN/AP cases and a new-state fixture. Fix the `--excel` path split.
4. **Run the prospective proximity study** before claiming a measured top-three quality level. If a later workflow requires a legally assigned jurisdiction rather than a nearby choice, that would be a different task requiring boundary or official address-to-station data.
